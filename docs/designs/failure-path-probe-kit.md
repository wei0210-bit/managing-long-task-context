## Problem Statement

David 用 Orca 跑多 agent 开发：协调者写封印合同，执行方实现，独立 Reviewer 审核，CI 全绿后合并。他在实际工作里最痛的只有一件事：返修循环。一个 PR 被审好几轮，每轮都要重新验收。

`docs/superpowers/plans/2026-10-15-context-skill-runtime-subtraction.md`（10 个 PR 的运行时减法方案）主要解决的是恢复时的 token 量和死代码，没有碰这个痛点。本设计把重心改到返修循环上，原方案降为次要。

## Demand Evidence

用户只有 David 一个人，需求证据来自他自己的 42 个真实任务账本（`.prime/context/`）：

- 12 个任务出现过 Reviewer FAIL；最多四轮（IMP-PRECHECK），STEP5-45、W1-P1、STEP6-46A、CONTEXT-SEARCH 各两到三轮。
- 每一轮找出的都是真缺陷，没有一例是只因为规则或变基触发的重审。
- 约 80% 的发现集中在读取文件、账本、报告的代码的失败路径上，反复出现的类别有：不可读目录被静默跳过还报 ok；符号链接目录、符号链接环、指向输出目录之外的符号链接；非 UTF-8 文件；畸形 JSON 和账本形状（类型不对、metadata 不是字典）；深层嵌套导致 RecursionError；孤立代理字符、U+2028 被 `splitlines` 当作换行；并发写入（按路径删锁）；发现和命名规则差异（`test_*.py` 与 unittest 默认的 `test*.py`、命名空间包同名遮蔽）。
- 规律：执行方每轮只修被报出来的那一个实例，Reviewer 下一轮又找到同一类的下一个成员。IMP-PRECHECK 四轮依次是不可读目录、符号链接目录、命名规则和 U+2028 和符号链接环、命名空间包。
- #87（检索功能）墙钟 12 小时：约 7.5 小时耗在执行方断线和模型被服务端拒绝上；三轮复审各自拦下了真缺陷，其中一个是 P1。

## Status Quo

- 协调者靠 Reviewer 一轮轮找缺陷；每轮 FAIL 后再派返修，每次返修都要重新起会话、重读合同、重跑验证。
- 文字规定已经试过：`references/preseal-checks.md` 要求「读取任务库、报告或落盘记录的改动，合同须含健壮性验收并实际覆盖异常路径」。它在 10 月 8 日随 #76（`2f125db`）加入，IMP-PRECHECK 的多轮 FAIL 正好发生在它生效期间；10 月 13 日随 #86 删除。
- W1-P1 的协调者裁决里出现过「交付前执行者须自跑复审者全部探针」，但只是针对单个任务写的，没有工具支撑。

## Target User & Narrowest Wedge

- 用户：David，以及他派出去的执行方 agent 和 Reviewer agent。
- 最窄切口：一套标准库写的失败路径探针，先接入一个真实入口，在历史缺陷版本上回放，证明它能抓到当时 Reviewer 抓到的问题。

## Constraints

- 只用 Python 标准库。根测试套件要在 macOS 系统 `python3`（3.9）和 3.12 上都能跑，CI 还有 Ubuntu 3.12。
- 预期行为（报错、跳过还是继续）由每个入口的合同来定，探针本身不规定。W1-P1 两轮 FAIL 的根源就是 Reviewer 的判据多规定了一条规格之外的执行顺序。
- 不可读文件的探针在 root 用户下会失效（root 能读 0000 权限的文件）；在 Windows 上不跑（本项目不支持 Windows）。
- 改动走 PR 进 main；按仓库约束，执行方只跑定向测试，全量交给 CI。

## Premises

1. 返修的主因是失败路径和边界类缺陷在第一次派工时没被覆盖，加上执行方只修实例、不修整类；不是规则触发的重审，也不是上下文太长。（David 同意）
2. 文字规定挡不住这类返修，必须是执行方能真的跑起来的探针和测试工具。（David 同意）
3. 运行时减法方案的 PR-1 到 PR-10 降为次要。PR-8（收窄 SA-MERGE-PR）缺乏证据，冻结；其余等探针工具证明有效后再排。（David 同意）
4. 执行方断线、模型不可用属于 Orca 的问题，本设计不做，只记入待办。（David 同意）
5. 成功标准三条一起看：探针在历史版本上能抓到当时的真缺陷；后续审核里目标类别的漏检数；首轮审核通过率只作参考。（原前提是「接下来 3 个 PR 里 2 个首轮通过」，按 Codex 冷读意见修订，David 同意）

## Cross-Model Perspective

Codex（gpt-6.1-sol，只读、无工具）冷读要点：

- 最强版本：一个可执行的交付前验证层，把真实审核里反复出现的失败模式变成执行方必须跑的测试；一次发现触发同类边界的系统排查，并留下可复核的证据。
- 最关键的证据：「each round the Executor fixes the single reported instance; the Reviewer then finds the next member of the same class」。问题不只是漏测，而是修复的单位太小。「修整类」必须落成一张明确的测试矩阵。
- 挑战的前提：原成功标准样本太小，PR 风险和审核力度也可能不同。应同时记录目标类别的漏检数，并用历史回放验证。（已采纳）
- 48 小时方案：`cases.py`、`adapters.py`、`runner.py` 三部分；CLI 适配器和函数适配器；断言由每个接入点从合同定义；先接一个真实入口，用历史缺陷验证。首版只做 4 类，跳过并发框架和十个架构 PR。
- 分歧：首版做 6 类而不是 4 类。深层嵌套和特殊字符写成探针很便宜，W1-C2 和 IMP-PRECHECK 都实际被这两类卡住过。

## Approaches Considered

### Approach A: 最小可行（已选）
6 类探针加一个真实入口加历史缺陷回放，约 1 天。

### Approach B: 理想架构
8 类全覆盖、接入所有读文件的入口、派工和审核规则、验收记录引用探针报告、指标统计脚本，约 3–4 天。没选：在证明有效之前铺开，风险是做出一套没人用的框架（这个仓库已经删过约 2,500 行这样的代码）。A 证明有效后按 B 扩展。

### Approach C: 历史发现逐条转成回归测试，由 CI 兜底
约 2 天。没选：只护住已知的入口，新代码照样会漏，正好是返修循环发生的地方。

## Recommended Approach

### 模块结构

首版共 3 个文件，都在 `tests/` 下（只给测试和执行方用，不进 Strict、Lite 的发布包；两个包的测试按白名单复制，新文件默认不进包）。工程评审 D1 选定这个结构：首版只有一个入口，不为还没出现的调用方预先拆模块。

| 文件 | 内容 |
|---|---|
| `tests/failure_probes.py` | 探针包本体，按下面的段落组织，约 400 行 |
| `tests/test_failure_probes.py` | 探针包自测：快照和清理在 6 类坏文件树上安全运行、判定规则、命令行退出码、故意写错的假入口被判 `fail` |
| `tests/test_failure_probes_replay.py` | 历史回放，见下文 |

`tests/failure_probes.py` 的段落：

- **变体**：每个类别一个生成函数，只生成「坏内容」本身：`Variant(category, name, kind, make)`，其中 `kind` 是 `file`、`dir`、`link` 之一，`make(path)` 在给定路径上造出这个变体（写字节、建链接、改权限）。每类包含一个正常对照和若干失败变体。生成函数不决定文件放在哪里。
- **适配器**：`CliAdapter(build_argv, cwd, env, timeout=30)`：用 `subprocess` 跑，记录 argv、工作目录、退出码、stdout、stderr、是否超时。子进程的环境只含适配器显式给出的变量，不继承调用者的 `PYTHONPATH`。子进程没能启动（例如工作目录进不去、解释器找不到）时，适配器返回启动错误，而不是抛到 runner 里。
- **runner**：逐个变体执行：用入口的 `place` 把变体放进一棵新建的入口文件树，调用适配器，做全局底线检查，再交给入口的 `expect` 判定；产出 JSON 报告。
- **入口登记**：每个入口登记 `Entry(name, scaffold, place, adapter, writable, expect, categories, exclude, known, pending)`：`scaffold(root)` 建一棵这个入口能正常工作的最小文件树；`place(variant, root)` 把变体放到入口真正会读的位置，并返回这个目标路径；`writable` 是入口允许写入的相对路径前缀；`expect(variant, target, result)` 按合同判定；`exclude` 是不适用的变体名到原因的映射；`known` 是已知基线，`pending` 是待协调者决定的新要求（都见「已知基线」）。首版只有 `context_search` 一项。接入第二个入口时，再把登记表拆成单独文件。
- **命令行**：`main(argv=None) -> int`，`argv` 为空时取 `sys.argv[1:]`；文件末尾 `if __name__ == "__main__": sys.exit(main())`。接口见下文「命令行与报告」。

函数调用适配器（直接调 Python 函数而不是起命令行）推迟到 B 阶段，首版没有入口用得到。

**`context_search` 的适配细节。** `scaffold` 在临时目录里 `git init`，建 `.prime/context/T/`、`docs/`、`CONTEXT.md`，每个正常文件都含固定标记词 `probetoken`；每个变体的内容也含 `probetoken`（字节层面写不进的变体除外）。`build_argv` 固定为 `[sys.executable, <仓库>/scripts/context_search.py, "search", "probetoken"]`，工作目录是临时仓库根。子进程环境只给 `PATH`（找 `git`）和 `HOME`。`writable` 是 `.prime/search/`（索引 `index.sqlite` 及其旁边的 `-journal`、`-wal`、`-shm` 文件）。「其他文件照常可搜到」就是指正常文件的路径出现在 `results` 里。`malformed_json` 变体走 `events.jsonl` 重建时，同一任务的 `events.jsonl` 出现在 `results` 里也算目标被处理过，不判 `vacuous`。

**import 方式只有一种。** 仓库的 `tests/` 没有 `__init__.py`，CI（R-004）用 `python3 -m unittest discover -s tests`，`tests/` 本身在 `sys.path` 上，所以测试按 `failure_probes` 导入这个模块。`failure_probes.py` 不匹配 unittest 默认的 `test*.py`，不会被当成测试收集。命令行用 `python3 tests/failure_probes.py` 直接运行：这个进程里只有 `__main__` 一份，文件本身也不 import 自己，不会出现同一模块的两份副本。`tests/test_failure_probes.py` 里断言 `failure_probes.__file__` 指向 `tests/failure_probes.py`，防止同名模块遮蔽（这正是 IMP-PRECHECK F-06 那一类）。

### 首版 6 类与变体

| 类别 | 变体 | 对应的历史缺陷 |
|---|---|---|
| `unreadable` | 不可读文件、不可读子目录、不可读根目录 | IMP-PRECHECK F-01 |
| `symlink` | 指向目录的链接、链接环、断链、指向根目录之外的链接 | IMP-PRECHECK F-02、F-05，W1-P2 |
| `encoding` | 非法 UTF-8 字节序列、合法 cp1252 文本、UTF-8 BOM | CONTEXT-SEARCH RF-01 |
| `malformed_json` | 截断 JSON、顶层不是对象、字段类型错误、条目不是字典、空文件 | STEP5-45 F-003..F-012 |
| `deep_nesting` | 100,000 层嵌套的数组、100,000 层嵌套的对象 | W1-C2 |
| `special_chars` | 孤立代理字符、U+2028、U+0085、`\r` 单独换行 | W1-C2、IMP-PRECHECK F-04 |

推迟：`concurrency`（并发写入）、`discovery`（发现和命名规则）。这两类和具体业务耦合太深，通用探针造不出来，留给 B 阶段按入口单独写。

### 两层判定：全局底线和入口合同

判定分两层，职责不重叠。

**全局底线（runner 对每个入口、每个变体都检查）。** 只有三条，是探针包明确声明的不变量；接入探针的入口必须接受，不能豁免：

1. 没有未捕获的 Python 异常栈：stdout 和 stderr 里不出现 `Traceback (most recent call last)`。
2. 没有超时：适配器在 `timeout` 内返回。
3. 受观察路径在运行后状态不变：跑之前和跑之后各拍一次快照，除 `writable` 前缀下的路径外，受观察路径的类型、大小、内容哈希、链接目标必须完全一致。它只证明最终状态，不证明运行中途没有写过又恢复。

受观察路径有三部分：探针建的整棵文件树；一个建在文件树之外的诱饵目录，「指向根之外的链接」就指向它，运行前后对它的内容做哈希；不可读的文件和目录，在降权之前记录内部内容，运行后先恢复权限、再核对一次。除此以外的路径不在观察范围内，报告里不为它们声称通过（工程评审 D7）。

快照本身必须能在这些坏文件树上安全运行：用 `os.walk(followlinks=False)` 和 `os.lstat`；符号链接只记录 `os.readlink` 的目标，不跟随；运行期间读不了的文件和目录只记录 `lstat` 元数据和「不可读」标记，不打开。临时目录清理前先把所有权限恢复成可读写，再删除。`tests/test_failure_probes.py` 对 6 类里的每一棵树都跑一次快照和清理，作为探针包的自测。

自测还要证明判定器会拒绝错误实现，而不只是能跑：测试里放一个故意写错的假入口（一个小脚本），分别抛出未捕获的异常栈、睡过 `timeout`、写到 `writable` 之外（包括写进根外诱饵目录和不可读目录内部）、静默忽略畸形 JSON 和深层嵌套。runner 对每种情况都必须判 `fail`，并给出对应的底线或 `expect` 原因。畸形 JSON 和深层嵌套没有历史回放可以对照，这几条是它们唯一的红灯证据（工程评审 D9）。

「静默漏掉文件」「是否必须记进 `skipped`」不在全局底线里，因为只有入口自己知道该读哪些文件。这些归入口合同。

**入口合同（每个入口的 `expect`）。** 写的是那个入口合同里的行为。每个变体判定前，runner 先检查 `place` 返回的目标路径确实被入口处理过（出现在结果、`skipped` 或错误信息里，或者合同明确说这类路径不读），否则判为 `vacuous`（空过）并算失败，防止坏文件放在入口根本不读的位置。

`context_search` 的 `expect` 覆盖首版全部变体。每一行写明依据：只有「#87 合同」「既有设计」两种依据的行是现成要求；标「新要求」的行是 #87 没有覆盖、本设计提出的行为，协调者在首个接入 PR 的合同里批准之前，这些行照常判定，但登记在 `pending`（待协调者决定，见下文），不计入退出码。「当前 main 实测」一列是 2026-10-15 在本机（3.9.6、3.12.13）手工跑出的结果，未实测的写「未测」。

| 类别 | 变体 | 合同要求 | 依据 | 当前 main 实测 |
|---|---|---|---|---|
| `unreadable` | 不可读（0000）的 `task-contract.json`、`docs/a.md` | 退出码 0；目标出现在 `skipped` 并带原因；其他可读文件照常可搜到 | 新要求（#87 只要求非 UTF-8 跳过，没提不可读） | 不符：整次检索失败，退出码 1，stdout 是 `Permission denied` 的 `error` JSON |
| `unreadable` | 不可读（0000）的 `docs/sub/` 子目录 | 同上：子目录路径出现在 `skipped` | 新要求 | 不符：`rglob` 吞掉 `PermissionError`，静默漏掉，`skipped` 为空，退出码 0 |
| `unreadable` | 不可读的仓库根 | 不适用（`excluded`）：`context_search` 没有根参数，根来自工作目录上的 `git rev-parse`，0000 权限下子进程连工作目录都进不去 | 入口形状 | — |
| `symlink` | 指向目录的链接、链接环、断链、指向根之外的链接（放在 `docs/` 下） | 退出码 0；不跟随、不索引，不要求记进 `skipped`；链接目标里的内容不出现在结果里 | 既有设计（`_sources` 排除链接）和 #87 第三轮复审通过的符号链接排除 | 符合：四种链接都不跟随，根外内容没有出现在结果里 |
| `encoding` | 非法 UTF-8 字节序列的 `task-contract.json`、`docs/*.md` | 退出码 0；目标出现在 `skipped`；其余文件照常 | #87 合同 D8/T2、RF-01 | 符合（`4d63796` 起） |
| `encoding` | 合法 cp1252 文档（含 0x80–0x9F 字节） | 同上：进 `skipped` | #87 合同 D8/T2（cp1252 这些字节不是合法 UTF-8） | 符合：进 `skipped` |
| `encoding` | 带 BOM 的 UTF-8 `docs/*.md` | 退出码 0；按正常文件索引，BOM 后的文字可搜到 | 新要求 | 符合：可搜到，行号 1 |
| `malformed_json` | 截断的 `snapshot.json`、顶层是数组、`items` 不是对象、item 不是字典、空文件 | 退出码 0；这个任务的条目可以缺失，但必须进 `skipped` 或回退到 `events.jsonl` 重建；其他任务照常 | #87 合同的重建标记回退（T2）覆盖 `{"rebuild":"required"}`；其余形状是新要求 | 大多不符：截断 JSON 让整次检索失败（退出码 1，`error` JSON）；`items` 是列表、item 是字符串时出现 `AttributeError` 异常栈（违反全局底线 1）；顶层数组和空文件退出码 0 但被静默忽略，既没进 `skipped` 也没回退 |
| `deep_nesting` | 100,000 层嵌套的数组和对象，分别写进 `snapshot.json` 和 `events.jsonl` 的一行 | 退出码 0；不出现 `RecursionError` 异常栈；目标正常索引或进 `skipped` 都算通过 | 新要求 | `events.jsonl` 不符：`RecursionError` 异常栈，退出码 1（违反全局底线 1）。`snapshot.json` 退出码 0、无异常栈，但被静默忽略。`json.loads` 实测：3.9 在 1,000 层就抛 `RecursionError`；3.12 到 5,000 层正常，100,000 层抛出。所以选 100,000 层，两个版本都会走到失败路径，要求又不依赖深度 |
| `special_chars` | `docs/*.md` 里含 U+2028、U+0085、单独 `\r` | 退出码 0；返回的行号与按 `\n` 分行的行号一致 | 新要求（同类问题在 IMP-PRECHECK F-04 被判为缺陷） | 不符：U+2028 和单独 `\r` 都让后面的行号多 1（真实第 5 行报成第 6 行）；U+0085 未单独测 |

`excluded` 由入口在登记时声明（`Entry.exclude`，变体名到原因），报告里单列并带原因，不算失败也不算通过；Reviewer 能看到每个排除项和理由。

**已知基线：让验收标准在有已知缺陷时也能用。** 入口登记时另有两张表，含义不同，分开存放（工程评审 D6）：

- `Entry.known`：已知失败。变体名到（issue 链接，允许的失败特征）。失败特征写明违反的是哪条底线或哪条 `expect`，再加 `reason` 里的关键片段，例如（底线 1，`AttributeError`）（工程评审 D5）。
- `Entry.pending`：待协调者决定。还没批准的「新要求」变体名。

两张表里的变体都照常运行。报告里分别单列为 `known` 和「待协调者决定」，都不计入退出码；退出码 0 的含义因此是「除已知失败和待决定的变体外没有失败」。规则有五条：

1. 基线只能缩小。新增 `known` 条目必须由协调者在合同里写明，并附 issue 和失败特征；执行方不能为了让退出码变 0 而加条目。
2. 某个 `known` 变体实际通过时，runner 打印 `KNOWN-NOW-PASSING <变体>` 并返回退出码 1，逼着修好它的 PR 同时把它移出基线。这条只对 `known` 生效：`pending` 里的变体通过或失败都只报告，不影响退出码。
3. `known` 变体失败了，但失败和登记的特征对不上（例如登记的是行号错误，实际却超时、越界写入或启动失败），判 `fail`，计入退出码。已知缺陷只豁免它自己，不豁免同一变体上的新退化。
4. 已批准的要求只能在修好缺陷后移出 `known`，不能放宽要求去迁就 main。`pending` 里的行，协调者可以在批准前改成与现状一致，但要在账本里记理由；批准后移出 `pending`，失败的转进 `known` 并附 issue，不再放宽。
5. 违反全局底线的变体也可以进 `known`，但只能附 issue，不能放进 `pending`：底线本身不是待决定的要求，`known` 只是如实记录「已知还没修」（工程评审 D2）。

首版的初始基线：`known` 收 expect 表里所有「不符」的行，各附 issue 和失败特征，其中 3 处违反底线 1：`items` 是列表、item 是字符串、`events.jsonl` 深层嵌套。`pending` 收其余仍未批准的「新要求」行，包括已经实测通过的 BOM 一行。

**合同没写到的变体怎么办。** 由协调者在派工前决定并写进合同；写之前，这个变体在报告里标 `undecided`，算失败而不是通过。这样「合同没说」会暴露出来，而不是被默默放过。上表「不符」的两行是已知偏差：协调者批准新要求后，它们就是首批由探针发现的缺陷，按真实缺陷开 issue，上表不为迁就现状而改。

### 命令行与报告

```text
python3 tests/failure_probes.py --entry context_search [--category unreadable ...] [--output <path>]
```

- 默认报告写到系统临时目录下的 `failure-probes/<entry>-<UTC 时间>.json`，不落在工作树里；`--output` 可以指定路径。报告不提交进仓库，账本只记报告路径和摘要。
- 退出码：0 表示除 `known` 和 `pending` 外，所有没跳过、没排除的变体都通过；`known` 变体意外通过，或失败特征对不上，也返回 1（见「已知基线」）；1 表示至少一个变体是 `fail`、`vacuous`、`undecided` 或 `adapter_error`；2 表示参数错误或入口不存在。
- `adapter_error`：适配器没能启动入口（子进程起不来、工作目录进不去）。它和 `fail` 分开记，因为这说明探针自己的搭建有问题，入口根本没跑；但同样算失败。
- 跳过不算通过：报告里单独计数，并写明原因（例如 `root-can-read-0000`）。只要有跳过，命令行最后一行就打印 `SKIPPED n`，交付和审核都要看到它。
- 报告每个变体一条记录，字段为 `category`、`variant`、`target`、`verdict`（`pass`、`fail`、`vacuous`、`undecided`、`adapter_error`、`excluded`、`skipped`）、`known`（是否在已知基线里，附 issue 和失败特征，以及特征是否对上）、`pending`（是否待协调者决定）、`reason`、`exit_code`、`timed_out`、`stdout_excerpt`、`stderr_excerpt`、`baseline`（三条全局底线各自的结果）。
