## Premises

1. 目标是开发速度和信息可靠传递，不是功能数量。
2. 执行控制功能分三类：账本核心保留；Orca 已有的删除；Orca 没有、但也不该由账本管的直接取消，不迁移。每项删除都要写明原缺陷由谁兜底。例外：租约、写入保护和 `orca_wait.py`，等换会话工作验证出替代能力后再定。（采纳 Codex 修订）
3. 慢的主要来源是全局规则、封印前基线试跑、常设授权条件和写死的验收深度，所以规则与 skill 一起改。这是待验证的假设：阶段 1 把新流程完整落地后，用小试点验证；不成立就不进入删除阶段。
4. Context 的积累用文件完成：账本事件、合同、`CONTEXT.md`、`docs/`、记忆都是普通文件，文件是唯一真源，不另建知识库。在文件之上加一层搜索引擎式的全文索引（倒排索引加相关度排序），让内容可检索。索引只是可随时从文件重建的缓存，不存独有信息；检索结果返回文件路径、行号、片段与核实时间，agent 再去读原文件。（David 2026-10-14 补充）
5. Ticket 各版本与变更理由、Worker 报告的事实与证据位置记入账本。验收判定由 Coordinator 写入账本（`decision` 字段），依据是 CI 运行和审核报告；执行状态归 Orca。依据：Orca `task-create --spec` 创建后不能改、没有历史，`task-update` 只有 status 和一段 result 文本（2026-10-14 用 `orca orchestration --help` 核实）。
6. 试点前先记基线，按下文公式判定。

### Ticket 版本的写入路径

- 一个 Ticket 对应账本的一个 `task_id`；Ticket 的一版就是一份封印合同（沿用 `publish_contract`，`version` 递增，`contract_history.py` 保留旧版全文）。
- 写入方：Coordinator。触发：改「做什么」（目标、范围、验收）时发布新版本，附变更理由；按原方案第 2.2 节，这类改动本来就要 David 确认。改「怎么做」（拆分、顺序、换 Worker 或模型）时只记一条账本决定，不发新版本。
- 与 Orca 的关联：每次 `task-create` 后，Coordinator 记一条账本事实，写 Orca task id、dispatch id 与合同版本号。阶段 0 核实 `publish_contract` 能否带附加字段；不能就用这条事实关联。
- 覆盖核对：Ticket 收尾时，用 `orca orchestration task-list` 对照账本关联事实。每个 Orca task 都要有关联，每个合同版本都要有变更理由；缺一条记为一次遗漏。

> 合同命令标 `ci` 后，`accept` 只核对一个 CI 运行的 `headSha` 与 `conclusion`，没有任何步骤核实这条命令确实被某个 CI 作业执行。任务专属命令（例如某个脚本的 `--check`，或只在本机有效的命令）被标成 `ci` 时，只要 CI 整体为绿就判 pass，命令实际从未运行。证据只取 `databaseId,headSha,conclusion,url`，不核对 workflow 名称和触发事件，同一头提交上其他 workflow 的成功运行也能满足条件；回归作业如果放在单独的 workflow，一个 run id 也证明不了「CI 全绿（含回归作业）」。

**Remedy**

> 规定 `ci` 类命令须写明覆盖它的 workflow 与作业，或只允许 CI 实际执行的固定集合（例如 `unittest discover` 收集的测试模块、包检查、回归条目）标 `ci`，并在发布合同时校验；CI 证据同时固定 workflow 名称、触发事件和各作业结论，并写明回归作业放在哪个 workflow。

### R1-7 — feasibility (blocking)

**Problem**

> 现有合同里 `worker_report_claim.commands` 是字符串列表，`worker_report.py` 的校验器和 `dispatch_spec.py` 都按此读取和展示。新口径要求每条命令带 `ci`／`review` 标记，设计没写标记存在哪个字段、`publish_contract` 如何校验、派工说明如何展示，也没写阶段 1 合并时已封印、没有标记的在途合同怎样验收（按旧口径复跑、全部视为 `review`，还是判 `unknown`）。

**Remedy**

> 写明标记所在的合同字段与校验规则、`dispatch_spec.py` 的展示方式，以及无标记旧合同的处理规则（例如沿用旧口径，或须发布新版本后才能按新口径验收）。

### R1-8 — completeness (blocking)

**Problem**

> 新判定只要求 `ci` 类证据的 `headSha` 等于「PR 头提交」，但没写 `accept` 从哪里取得 PR 头提交（`gh pr view`、本地 HEAD 还是手填），也没要求审核报告里的命令运行在同一提交上。SA-MERGE-PR 的 `--match-head-commit <已验证提交>` 在新口径下没有定义「已验证提交」：验收后若又推了提交，CI 在新头提交上为绿，旧提交上的 `decision=pass` 记录和审核报告仍可能被用来合并。旧流程靠协调者在集成提交上复跑来绑定提交，取消复跑后这一绑定没有替代。

**Remedy**

> 写明 PR 头提交的取得方式；要求审核报告的 `code_revision` 等于该提交；把「已验证提交」定义为验收记录中的这个提交，头提交变化后须重新审核并重新验收。

### R1-9 — feasibility (blocking)

**Problem**

> `review` 类判定只写「审核报告里有对应日志且退出码为 0」。现有校验器绑定一个工作区根目录，要求输出文件在根目录内、按摘要比对、HEAD 一致且工作区干净；而 `dispatch_spec.py` 要求审核者的写盘命令在「所有 Git 工作树之外的独立 Git 副本」里运行，`accept` 在协调者工作区里读不到也核不了这些日志。设计没选是把审核日志复制进证据目录并用摘要固定，还是只信审核报告自报的退出码；后者比现行校验弱，属于放宽验收的决定。

**Remedy**

> 写明审核报告的格式（例如沿用 worker report 合同）、日志如何复制并用摘要固定、`accept` 用哪个根目录校验，以及是否接受自报退出码。
