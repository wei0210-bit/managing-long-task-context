## Problem Statement

当前 `managing-long-task-context` 把两类需求混在一个工作流中：

1. 普通单 Agent 长任务需要低成本地恢复目标、当前状态和下一步。
2. 多 Agent、高风险任务需要控制事实来源、验收标准、冲突、交接、证据和完成声明。

现有 skill 的核心原则正确，但对普通任务过重，对严格任务又存在七项实质性缺口：冲突状态可能被更新逻辑覆盖；生成给 Agent 的文字 brief 丢失来源、证据和范围；完成门禁只检查证据字段是否填写，不能确认引用的证据是否真实存在或有效；SHA-256 摘要只能检测内容变化，不等于身份认证；brief 的条目选择缺少优先级、时效和稳定预算；URL 证据边界不明确；审计探针缺少隔离规范。

因此，不继续给一个 skill 增加模式开关，而是拆成两个由人手动选择、运行时相互独立的 skill，并只共享一个极小的交换格式。

v1.1 不改变上述架构选择，只收紧四个协议边界：任务恢复不冒充运行时续跑；进行中动作必须显式记录且恢复时先核实；交接必须区分排队、消费与确认；运行事件、trace 和 Agent 报告不得自动升级为验收证据。

## What Makes This Cool

这套设计不把“上下文管理”等同于保存聊天记录。它把上下文分成两个价值层：

- Lite 优化恢复速度，用最少的高信号内容让下一轮工作继续前进。
- Strict 优化认知完整性和交付闭环，防止“记错且不自知”以及“系统说完成但用户没有得到结果”。

Agentic-Dev 的真实经验成为取舍依据：每个机制必须对应一个发生过的失败，并且要在后续真实任务中证明它确实阻止了该失败。

## Constraints

- 用户手动选择 Lite 或 Strict，不实现自动分类器，也不增加路由 skill。
- 两个 skill 共享交换格式，但不共享运行时、存储引擎或默认工作负担。
- Lite 必须可以只靠 Markdown 和实时项目观测工作，不要求 Python 包或数据库。
- Strict 可以保留当前 Python 事件账本，但必须修复已知正确性问题后才能作为完成控制器使用。
- 聊天摘要、Agent 报告和缓存快照只能用于导航，不能替代原始证据。
- `resume` 只恢复已持久化的任务上下文，不恢复模型隐藏推理、未持久化消息、权限会话、工具进程、网络连接、后台 executor 或任意 mid-turn runtime。
- 无法核实原运行时状态时，进行中动作必须标记为 `unknown`，不得因为“可能没跑完”而自动重试有副作用的动作。
- 能从 Git、文件系统、测试或外部系统实时读取的状态，不在 Lite 中重复维护为手写事实。
- 本轮只产出设计，不修改两个 skill 的实现。
- 当前工作目录不是 Git 仓库，因此设计阶段不假定已有版本发布、CI 或团队同步能力。

## Premises

- `context-lite` 面向单 Agent、多轮或跨天、低风险任务，目标是可靠恢复，而不是审计。
- `context-strict` 面向多 Agent、外部副作用、冻结验收、高风险结论或需要独立验证的任务。
- 是否使用哪一个 skill 由人决定。两个 skill 的 description 明确边界，但不得在运行时静默升级或降级。
- Lite 只保存目标、当前阶段、确认过的决策、证据引用、阻塞和下一步。
- Strict 保存发布者拥有的任务合同、追加事件、来源与验证状态、冲突和过期、依赖、交接、链路证据及完成门禁。
- Strict 的 `snapshot.json` 是由控制账本派生的状态快照，不是 Agent 或工具进程的运行时 checkpoint；恢复 Strict 任务同样不代表恢复原 turn。
- Lite 可显式导出交换包并升级到 Strict；Strict 可导出一个只读恢复摘要供 Lite 风格阅读。升级不删除原始 Lite 记录，降级不改变 Strict 的事实账本。
- 两个 skill 共享概念词汇和交换格式，不共享底层代码。共享代码不是目标，行为边界稳定才是目标。
- 任何字段、检查或流程如果说不清它阻止了哪一种失败，就不进入默认路径。

## Recommended Approach

采用两个完全独立的 skill，加一个版本化的最小交换格式。

### 1. `context-lite`

#### 使用边界

适合：

- 一个主要执行 Agent。
- 任务会跨多轮、上下文窗口或工作日。
- 错误可以通过常规代码审查或测试恢复。
- 用户主要担心中断后重复探索、忘记决策或不知道下一步。

不适合：

- 执行者和验收者需要职责分离。
- 存在发布、付款、删除、发送消息等外部副作用。
- 完成声明需要逐条证据或审计记录。
- 多个 Agent 并行写入同一任务状态。

#### 用户工作流

只提供四个动作。`task-id` 必须匹配 `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`，禁止路径分隔符和 `..`：

1. `start`：目标目录不存在时建立第一份 `NOW.md`；同一 task-id 和同一目标重复调用返回现有任务且不覆盖，目标不同则报错并要求新 task-id。
2. `checkpoint`：先刷新动态来源，再把相对时间规范为 UTC 绝对时间，把“这里”“刚才那个任务”等指示性引用改为稳定定位符，最后用临时文件加同目录原子 rename 替换 `NOW.md`；不追加聊天历史。超过 80 行时失败并报告超限章节，不静默截断。
3. `resume`：读取 `NOW.md` 后重新观测 `Refresh On Resume` 和 `In Flight` 的 `recovery_ref`；任何无法刷新项标记 `unknown`，同时保留原记录仅作历史提示。它恢复任务级上下文，不续跑先前 turn，也不自动重试进行中的动作。
4. `finish`：默认执行 `--archive`，原子移动到 `.context-lite/archive/<task-id>-<timestamp>/`；`--delete` 必须由用户显式选择并确认。两种方式都不得自动生成长期记忆。

#### 持久化文件

```text
.context-lite/<task-id>/
├── NOW.md
└── context-transfer.json   # 仅在显式导出或升级时生成

.context-lite/archive/
└── <task-id>-<timestamp>/
```

`NOW.md` 使用固定且短小的结构：

```markdown
# <task-id>: <目标>

Updated: <timestamp>
Phase: <current phase>

## Acceptance
- <当前任务的完成条件>

## Current State
- [STATE-01] <当前事实> | mutable: true | source: <引用> | refreshed_at: <timestamp> | refresh_ref: <命令或路径>

## Decisions
- <决定> | why: <原因> | evidence: <路径、测试或链接>

## In Flight
- [RUN-01] <动作> | owner: <user/agent> | status: pending/blocked/unknown | started_at: <UTC timestamp> | correlation_ref: <job/tool/session ID> | recovery_ref: <只读核实方式>

## Blockers
- <阻塞或 none>

## Next
1. <唯一的第一步>
2. <后续步骤，最多三项>

## Refresh On Resume
- STATE-01 -> <需要重新读取或验证的动态来源>
```

默认限制：

- `NOW.md` 不超过 80 行、8000 个 Unicode 字符，单行不超过 500 字符。
- `Next` 不超过 3 项，并明确唯一的第一步。
- 不复制长日志、完整对话或大段代码，只保留可按需读取的文件路径、命令、测试名或 URL。
- `checkpoint` 必须把相对日期转成 UTC RFC 3339 绝对时间，并把指示性引用改为完整、稳定的路径、symbol、PR/issue、job/message/tool ID、URL、精确命令或精确错误字符串。跨 workspace 的文件引用必须同时记录来源 workspace，不得只写相对路径。
- `In Flight` 为可选章节；没有进行中动作时写 `none`。每项使用稳定 RUN ID。`correlation_ref` 只用于定位外部运行，`recovery_ref` 只允许观测其真实状态，二者都不授权自动重试。
- 可变化的信息放入 `Refresh On Resume`，不得伪装成永久事实。
- 决策必须写明原因；影响完成判断的结论必须带证据引用。
- `checkpoint` 写入失败时保留原 `NOW.md`；临时文件不得被 `resume` 当作有效状态。
- 超限错误必须建议三种确定性处理：把原始内容移到外部 artifact 并只留引用、删除已解决状态、或拆分 task-id；不得自动删除 Acceptance、Blockers 或唯一第一步。

`resume` 不直接相信 `Current State`。每条 mutable 状态必须有稳定 STATE ID 和 `refresh_ref`；`Refresh On Resume` 逐条映射该 ID。某项无法刷新时只把对应状态标记 `unknown`，不得让无关状态失效，也不得继续沿用旧值。每个 `recovery_ref` 只能更新与其稳定 RUN ID 匹配的进行中项；外部系统不可查询、返回含糊结果或定位符失效时，该项保持 `unknown`。只有观测到明确的未执行状态，且动作本身可安全重试或用户再次授权，才可重新执行。

### 2. `context-strict`

`context-strict` 从当前 `managing-long-task-context` 演进。保留其发布者合同、追加事件和可重建快照模型，Python 导入名在 `context-strict` 的首个稳定 minor release 中继续支持 `managing_long_task_context`。

#### 默认工作流

1. 发布者创建并确认带版本的合同。
2. release gate 验证合同结构与内容完整性。
3. 执行者把观察、假设、决定、问题和已验证事实分类型写入事件账本。
4. checkpoint 只记录阶段增量和下一步；handoff brief 从受控状态生成，并以稳定 `handoff_id` 记录交接状态。
5. 接收者消费 handoff 后显式确认；验证者重新解析证据并检查完整执行链路。仅排队或仅生成 Agent 报告不算交接完成。
6. completion gate 对每条验收标准验证证据存在性、类型、时间、范围和必要链路，不接受执行者的自我声明代替证据。

#### 必须修复的七项正确性问题

- S1：`update_item` 必须保留显式 `conflicted` 状态，不能在同一次更新中被“已有证据”逻辑重新改回 `active`。
- S2：Markdown brief 中的每条关键事实必须包含来源、证据、适用范围、核实时间和状态；摘要不得比结构化 packet 丢失控制信息。
- S3：条目选择按 `required > conflicted > blocker > decision > verified fact > assumption` 排序。Strict schema v2 首版使用确定性的字符预算而不是依赖特定 tokenizer：默认 `max_chars=8000`；同级按严重度、更新时间倒序、item ID 字典序排序。required 和 conflicted 永不静默截断；它们单独超预算时返回 `BRIEF_REQUIRED_OVERFLOW`，不生成可能误导的 prompt。
- S4：证据映射通过可插拔 resolver 检查可达性、完整性、时效和范围；resolver 不宣称自动理解任意证据的语义。语义支持由类型化 verifier 或独立验证者确认并绑定到验收项。
- S5：合同中的 SHA-256 字段命名和文档表述改为 `integrity_digest`。它只证明发布后内容未被无意修改，不声称证明确认者身份。需要身份认证时由外部签名或受信存储提供。
- S6：completion gate 必须拒绝空证据、无效引用、过期证据、范围不匹配、冲突未解决、关键 hop 缺失和交付回执缺失。resolver 可以返回 `unknown`，但任何必需项的 `unknown` 都阻止 completion pass。
- S7：`audit` 必须始终输出扫描数量。坏样本探针在临时隔离账本中调用与生产相同的解析和 gate 代码，输出 probe ID、扫描数和预期拒绝结果，不向真实账本写入探针事件。

#### 持久化文件

继续使用当前布局，避免无必要迁移：

```text
.prime/context/<task-id>/
├── task-contract.json
├── events.jsonl
└── snapshot.json
```

导出的 `context-transfer.json` 是派生物，不是第四个事实来源，可以随时从合同和事件重建。

#### 术语与角色

- `publisher`：创建目标、范围和验收标准，并有权发布更高合同版本的用户或明确授权角色。
- `executor`：实施任务的人或 Agent，不能放宽验收标准。
- `validator`：不接受 executor 自我声明、重新解析证据并签署验收映射的人、Agent 或确定性程序。
- `required hop`：合同中命名的关键执行边界；每个 hop 必须有独立证据表明输入到达并产生预期输出。
- `delivery receipt`：证明目标对象实际收到或保存了指定产物的证据，而不是“发送动作已调用”的日志。
- `control_event`：写入 Strict `events.jsonl`、参与状态重建和 gate 的规范事件。
- `runtime_event`：Agent、工具、队列或宿主运行时产生的执行信号；它可帮助定位，但默认不进入控制账本，也不自动成为证据。
- `trace_span`：用于可观测性的调用链片段；成功状态只说明该 span 的运行结果，不证明验收陈述成立。
- `evidence`：由合同允许的 resolver 定位、检查完整性与范围，并由 verifier 或 validator 绑定到具体验收项的产物。
- `scope mismatch`：证据对应的仓库版本、模块、环境、目标对象或时间范围与验收项要求不一致。
- `real task`：会产生用户实际需要的项目产物的任务，不是 fixture、演示或只为通过测试构造的流程。

#### Strict schema v2 最小数据模型

合同保留现有字段并增加 `schema_version: 2`、`workspace_root`、可选 `evidence_roots`，以及 actor 到 `publisher/executor/validator` 的角色授权表。每条验收标准至少包含：

```json
{
  "id": "AC-01",
  "statement": "重复回调只产生一笔写入",
  "required_evidence_types": ["test-report"],
  "required_scope": {"module": "payment-callback", "environment": "test"},
  "max_evidence_age_seconds": 3600,
  "required_hops": ["callback-entry", "idempotency-check", "transaction-write"],
  "required_delivery_types": [],
  "independent_validation_required": true
}
```

当 `independent_validation_required` 为 true，签署该验收映射的 actor 必须拥有 validator 角色，且不能是该验收项所引用证据的提交者或执行者。completion gate 从合同授权表核对角色；角色缺失或职责未分离时结果为 fail。false 只允许用于合同明确标注的低风险标准。scope 必须覆盖 `required_scope`；证据年龄按 completion gate 当前 UTC 时间减 `generated_at` 计算，不得超过 `max_evidence_age_seconds`。不同证据类型需要不同窗口时，由验收项增加 `evidence_freshness_by_type` 覆盖默认值。

事件使用稳定 envelope：

```json
{
  "schema_version": 2,
  "event_id": "uuid-v4",
  "seq": 42,
  "task_id": "TASK-001",
  "event_type": "evidence-recorded",
  "actor": "validator-01",
  "recorded_at": "2026-08-27T00:00:00Z",
  "idempotency_key": null,
  "payload": {}
}
```

`event_id` 使用标准 UUIDv4；不依赖 UUIDv7。调用者执行可重试动作时必须提供稳定、不可含凭据的 `idempotency_key`，不可重试动作允许为 `null`。

证据 payload 的共同字段为：

```json
{
  "evidence_id": "EV-018",
  "kind": "test-report",
  "locator": "artifacts/test-018.json",
  "artifact_digest": "sha256:...",
  "repo_revision": "<git commit or null>",
  "command": "pytest tests/test_callback.py",
  "exit_status": 0,
  "generated_at": "2026-08-27T00:00:00Z",
  "observed_at": "2026-08-27T00:01:00Z",
  "expires_at": null,
  "scope": {"module": "payment-callback", "environment": "test"},
  "resolver_status": "pass",
  "resolver_codes": [],
  "verified_by": "validator-01",
  "verified_at": "2026-08-27T00:02:00Z",
  "correlation_refs": {
    "provider": "agentscope",
    "session_id": "...",
    "reply_id": "...",
    "message_id": "...",
    "tool_call_id": "...",
    "trace_id": "..."
  }
}
```

不适用字段使用 `null`，不得伪造默认值。`correlation_refs` 为可选定位信息，只帮助从证据回查运行记录，不能提高 `resolver_status` 或验收结果。手工判断使用 `kind: manual-attestation`，必须包含判断者、判断方法和被检查的原始证据引用。

验收映射至少包含 `criterion_id`、`result`、`evidence_ids`、`covered_hops`、`delivery_receipt_ids`、`validated_by` 和 `validated_at`。三态传播规则固定为：

1. 任一必需检查为 `fail`，验收项为 `fail`。
2. 没有 `fail`，但任一必需检查缺失或为 `unknown`，验收项为 `unknown`。
3. 只有全部必需检查为 `pass`，验收项才是 `pass`。
4. 只有全部验收项为 `pass` 且全局冲突、合同和交付门禁通过，completion 才能通过；`unknown` 永远不是完成。

resolver 分四层返回带错误码的结果：`resolve` 检查目标可读取，`validate_integrity_and_freshness` 检查摘要、版本和时间，`match_scope` 检查适用范围，`verify_claim` 由类型化 verifier 或 validator 判断它是否支持具体验收项。前三级通过不能自动代替第四级。

`kind` 选择 resolver，`locator` 只保存该类型内部的地址，不重复 `kind:` 前缀。本地 resolver 的首版契约：

- `kind: file`，`locator: <workspace-relative-path>#<optional-fragment>`：以合同的 `workspace_root` 为基准；`realpath` 必须位于 workspace root 或显式 `evidence_roots` 内。符号链接只有最终目标仍在允许根目录内才可读取。存在、可读、摘要匹配且未过期才通过前三层相应检查。
- `kind: git-commit`，`locator: <40-hex-sha>`：以 `workspace_root` 所在 Git 仓库为准，必须能被 `git cat-file -e <sha>^{commit}` 解析。验收项要求 exact revision 时必须相等；要求 ancestor 时用祖先关系检查。
- `kind: test-report`，`locator: <workspace-relative-path>`：目标必须是 JSON，至少含 `schema: context-test-report/v1`、`command`、`exit_status`、`generated_at`、`repo_revision`、`scope` 和 `artifact_digest`。报告内 `artifact_digest` 覆盖除顶层 `artifact_digest` 字段自身外的 RFC 8785 canonical JSON。只有退出码为 0、摘要正确、版本和 scope 匹配且在 freshness 窗口内才可通过前三层；是否支持验收项仍由 verifier 判断。

共同错误码至少包含：`MALFORMED_LOCATOR`、`OUTSIDE_ALLOWED_ROOT`、`NOT_FOUND`、`PERMISSION_DENIED`、`DIGEST_MISMATCH`、`STALE`、`SCOPE_MISMATCH`、`UNSUPPORTED_KIND`、`NETWORK_BLOCKED`。错误码映射为 fail 还是 unknown 必须由确定性表测试：证据本身错误为 fail，环境暂时无法观测为 unknown。

`delivery-receipt` evidence 额外包含 `channel`、`target_id`、`artifact_ref`、`external_id`、`sent_at`、`observed_at` 和 `verification_method`。目标系统没有可读回执时必须是 `unknown` 或人工验证，不得从发送函数返回值推断成功。

#### 交接状态与运行时边界

handoff 是控制账本中的状态机，而不是一条“已发送”日志：

```json
{
  "handoff_id": "HO-018",
  "from_actor": "executor-01",
  "to_actor": "validator-01",
  "payload_digest": "sha256:...",
  "source_event_ids": ["uuid-v4"],
  "transport_ref": "queue-or-message-id",
  "state": "prepared|enqueued|consumed|acknowledged|failed|unknown",
  "recorded_at": "2026-08-27T00:00:00Z",
  "acknowledged_at": null,
  "correlation_refs": {"provider": "agentscope", "session_id": "...", "message_id": "..."}
}
```

- 状态只允许按 `prepared -> enqueued -> consumed -> acknowledged` 前进；`failed` 和 `unknown` 是阻塞态，恢复正常必须追加带原因的新 control event，不得覆盖旧事件。
- `enqueued` 只证明 transport 接受了载荷，`consumed` 只证明接收端取到载荷；相关工作交接只有到 `acknowledged` 才闭环。缺少确认、payload digest 不匹配或接收者身份不匹配时，相关 completion 为 `fail` 或 `unknown`。
- worker 的自由文本报告、工具成功返回、运行时 task `completed`、trace span `OK` 和消息投递成功都只是运行时 claim。除非合同允许相应 evidence kind、resolver 通过且 validator 绑定到验收项，否则不得成为 pass。
- 首版 Strict 不实现可靠队列、lease 或 Agent 运行时续跑；transport 由宿主系统负责。Strict 只记录其稳定引用、核实状态和确认事件。
- 先把 canonical handoff 状态追加到控制账本，再产生通知或 UI 投影；通知、inbox 和缓存是可重建镜像，不是第二事实来源。
- 高频 token、streaming 或 span 事件不得逐条写入 `events.jsonl`。只保存能支撑恢复或审计的稳定 `correlation_refs`；原始 telemetry 继续留在其运行时系统。
- 恢复时若宿主运行时的实时状态可查询，实时观测优先于旧快照；无法查询则为 `unknown`，绝不从 stale snapshot 推断仍在运行或已经完成。

#### 摘要、并发、损坏与迁移

- 所有 JSON 摘要使用 RFC 8785 JSON Canonicalization Scheme，UTF-8 编码和 SHA-256，格式为 `sha256:<lowercase-hex>`。时间统一为 UTC RFC 3339 秒级字符串，禁止 NaN 和 Infinity。
- 合同 `integrity_digest` 覆盖除 `seal.integrity_digest` 自身外的完整合同。事件幂等 payload 摘要覆盖规范化的 `event_type`、`actor` 和 `payload`，不覆盖 `event_id`、`seq`、`recorded_at`。
- 事件链以 32 个零字节作为 H0。第 n 项使用 `Hn = SHA256(Hn-1 || UTF8(RFC8785(event_n)))`，其中 `event_n` 包含完整事件 envelope；存储格式仍为 `sha256:<lowercase-hex>`。
- `snapshot.json` 包含 `last_seq` 和截至该事件的 `event_chain_digest`。打开任务时先在锁内验证账本：只有 snapshot 落后且其 `last_seq` 对应账本前缀摘要仍匹配时才自动重建。snapshot 已覆盖前缀的摘要不匹配、snapshot 超前、账本有缺口或事件损坏时停止所有 gate，并要求显式 repair。

- v2 支持同一台主机上的多 Agent。每次分配 `seq`、追加事件、`fsync` 和原子替换 snapshot 都在任务目录的排他文件锁内完成。
- `event_id` 全局唯一；相同 `idempotency_key` 和相同规范化 payload 重试为 no-op，相同 key 不同 payload 返回冲突。
- snapshot 必须从连续 `seq` 的事件重建。发现重复序号、缺口、非法 JSON 或半写尾记录时，所有 gate 停止并报告损坏位置。
- Strict schema v2 首版不自动截断损坏的 `events.jsonl`。显式 repair 先完整备份任务目录，再只处理已确认的无效尾部并重建 snapshot。
- 网络文件系统和多主机锁不在 Strict schema v2 首版支持范围；需要多主机并发时改用有事务保证的数据库后端。
- 现有无 `schema_version` 数据视为 legacy v1。迁移先备份，发布者重新发布更高版本的 v2 合同，再追加 `schema-migrated` 事件；旧 verified fact 若缺少 v2 证据字段，迁移后降为 unverified observation，必须重新验证。
- Python 导入名 `managing_long_task_context` 在 `context-strict` 首个稳定 minor release 中保留并发出 `DeprecationWarning`，下一个 major release 才可删除。兼容测试同时覆盖新旧导入名。
- 回滚只切回迁移前的只读备份，不逆向删除 v2 事件。

#### Strict schema v2 首版 URL resolver 安全边界

- URL 证据使用 `kind: url` 和裸 HTTPS URL `locator`，不添加 `url:` 前缀。
- 默认 URL resolver 只做 HTTPS 语法、无内嵌凭据和 locator 规范检查，因此状态最高为 `unknown`，不能单独支持 completion pass。
- 可选网络 resolver 必须配置 hostname allowlist；拒绝 loopback、私网、链路本地地址和非 HTTPS 协议。
- 请求超时 5 秒、响应上限 1 MiB、最多 3 次重定向；每次重定向重新校验 hostname 和解析后的 IP；不自动附带 cookie、Authorization 或本机凭据。
- 可选 resolver 记录最终 URL、状态码、响应摘要和观测时间。它仍只证明可达性和内容完整性，语义支持需要 verifier 或 validator。
- 持久化的 `resolver_status` 只是历史观测。每次 completion gate 都必须重新运行所有必需 resolver；只有合同显式定义 freshness 窗口且历史 gate-run 仍在窗口内时才可复用，并且复用记录必须绑定同一合同版本、证据摘要和 scope。

### 3. 共享交换格式

交换格式版本为 `context-transfer/v1`：

```json
{
  "schema": "context-transfer/v1",
  "transfer_id": "uuid-v4",
  "content_digest": "sha256:...",
  "task_id": "TASK-001",
  "generated_at": "2026-08-27T00:00:00Z",
  "source_mode": "lite",
  "goal": "...",
  "source_context": {
    "workspace_root": "/absolute/source/workspace",
    "repo_revision": "<git commit or null>",
    "task_record": ".context-lite/TASK-001/NOW.md"
  },
  "acceptance": ["..."],
  "state_items": [
    {
      "id": "STATE-01",
      "statement": "...",
      "item_type": "observation",
      "verification_status": "unverified",
      "source_refs": ["file:path#section"],
      "source_event_id": null,
      "verified_at": null,
      "scope": {"module": "..."},
      "mutable": true,
      "refresh_ref": "git:status"
    }
  ],
  "in_flight_items": [
    {
      "id": "RUN-01",
      "action": "...",
      "owner": "agent-01",
      "status": "pending|blocked|unknown",
      "started_at": "2026-08-27T00:00:00Z",
      "correlation_ref": "job-or-tool-id",
      "recovery_ref": "只读核实方式"
    }
  ],
  "decisions": [
    {
      "id": "DEC-01",
      "statement": "...",
      "reason": "...",
      "evidence_refs": ["file:path#section"],
      "source_event_id": null
    }
  ],
  "evidence_refs": ["..."],
  "refresh_sources": ["git:status"],
  "blockers": ["..."],
  "next_actions": ["..."]
}
```

规则：

- v1 只包含恢复执行所需的信息，不承载完整事件历史。
- Lite 导入 Strict 时，所有 `state_items` 都写为 observation；即使 transfer 写着 `verified`，也只有 Strict resolver 和 validator 重新验证后才能成为 verified fact。
- `source_context` 和 `in_flight_items` 均可选。存在跨 workspace 相对定位符时必须提供 `source_context.workspace_root`；导入端不得把来源绝对路径当作目标 workspace 内路径。
- Strict 导入 `in_flight_items` 时只能创建 observation 或 pending-operation control event，不得据此恢复原 runtime 或自动重试动作。无法通过 `recovery_ref` 核实的项保持 `unknown`。
- Strict 导出时在可用时保留 `source_event_id` 和证据引用，但导出包本身不得被 completion gate 当作证据。
- `transfer_id` 用系统标准 UUIDv4 生成，在一次导出时写入并随文件保存，不需要第三方运行时。`content_digest` 使用 RFC 8785 canonical JSON 和 SHA-256，覆盖除 `content_digest` 自身外的完整交换包。Strict 把已导入 ID 和摘要记录为事件；重复导入相同 ID 和相同摘要是 no-op，相同 ID 但内容不同是冲突。
- 导入到已有 Strict 任务时，`task_id` 必须与合同一致。显式 remap 必须提供目标 task-id，并追加包含原 ID、新 ID 和 actor 的映射事件；不得静默合并。
- Strict 任务尚无发布者合同，导入只能进入 staging，release gate 在合同发布并确认前保持关闭。
- 未知字段必须被忽略；不兼容的主版本必须拒绝导入。
- 导入和导出都不删除源数据。

#### 一条完整判定示例

发布者在 AC-01 中要求 `test-report` 和三个 required hops。executor 运行测试，生成绑定当前 commit、命令和退出码的 EV-018；validator 重新读取报告，resolver 确认可达、摘要、时效和范围，类型化 verifier 确认报告支持 AC-01，并把三个 hop 的证据 ID 写入验收映射。只有这些结果全部为 pass，AC-01 才为 pass。如果报告文件随后被删除，resolver 变成 fail；如果网络或权限导致无法读取，则变成 unknown。两种情况都会使 completion 不通过。

## Failure-Mode Coverage

| 已发生或已识别的失败 | Lite | Strict | 验证方式 |
|---|---|---|---|
| 中断后不知道做到哪里 | `NOW.md` 的 Phase、Current State、Next | checkpoint 与 snapshot | 新会话只读受控文件即可说出唯一下一步 |
| 推断被写成事实 | 结论只作当前状态，影响完成时必须带引用 | observation、assumption、verified-fact 分型 | 已知无来源事实样本必须被拒绝 |
| 旧状态继续被使用 | `Refresh On Resume` 实时刷新 | mutable、TTL、resume gate | 注入过期样本后 resume 不得通过 |
| 把任务恢复误当成运行时续跑 | `In Flight` 加 recovery ref；不可查询即 unknown | snapshot 明确不是 runtime checkpoint | 只有启动日志而无终态时不得宣称继续运行或自动重试 |
| 文档或证据指针漂移 | 恢复时检查引用可达性 | audit 与 evidence resolver | 删除目标文件后检查必须失败或 unknown |
| 机制写了但没使用 | finish 前记录一次真实使用结果 | 审计探针和真实任务验收 | 下一项真实任务中观察机制是否阻止错误 |
| 检查通过但链路是空接线 | 不承担该保证，必要时改用 Strict | required hops 与真实 E2E 证据 | 缺任一 hop 的已知坏样本必须失败 |
| Agent 声称完成但未交付 | Lite 只记录，不提供强保证 | 独立 gate 与交付回执 | 执行报告存在、目标交付缺失时 completion 失败 |
| handoff 已排队但接收者未确认 | 记录为进行中，不声称闭环 | prepared/enqueued/consumed/acknowledged 状态机 | 只有 queue/message ID 而无 ack 时 completion 不通过 |
| trace 或工具成功被误当成验收证明 | 仅作定位引用 | runtime event、trace span 与 evidence 分层 | 注入 task completed 或 span OK、但缺验收证据时 gate 必须阻止 |
| 冲突事实被静默覆盖 | 冲突时提示升级 Strict | 追加冲突事件并阻止 gate | 冲突更新后状态保持 conflicted |

## Approaches Considered

- 采用方案：两个完全独立的 skill，共享极小交换格式。它保持 Lite 的低成本，同时允许 Strict 独立强化。
- 否决：两个 skill 共享同一个底层引擎。底层复杂度会重新渗透到 Lite，并扩大变更耦合。
- 暂不采用：增加第三个人工路由 skill。当前用户可以手动选择；只有真实使用持续出现误选时才增加。
- 否决：直接引入 AgentScope runtime、消息总线、长期记忆后端或完整 AgentState。它们可作为宿主和观测来源，但本设计需要的是跨宿主的最小控制协议，而不是绑定某个运行时。

## Success Criteria

### Lite

- 新会话只读取 `NOW.md` 和其中明确列出的实时来源，就能准确说出目标、当前阶段、阻塞和唯一第一步。
- 对三个真实单 Agent 长任务试用后，`NOW.md` 均不超过 80 行，且没有复制完整聊天记录或长日志。
- 动态来源无法刷新时输出 `unknown`，测试确认不会沿用旧值作为事实。
- checkpoint 把相对时间和指示性引用规范为绝对时间与稳定定位符；跨 workspace 相对引用缺少 `source_context` 时导出或导入失败。
- 只有后台动作启动记录而没有可核实终态时，`resume` 把对应 RUN 项标为 `unknown` 且不自动重跑；一个 `recovery_ref` 只能更新匹配的 RUN ID。
- 用户可以显式导出 `context-transfer/v1`，且 Strict 导入后不会自动把 observation 提升为 verified fact。
- 常规使用路径不需要安装 Python 包或维护事件账本。
- `start` 重复调用、checkpoint 原子写失败、80 行或 8000 字符超限、单项 refresh 失败、archive 和显式 delete 都有确定性测试。

### Strict

- 当前测试继续通过，并新增覆盖：冲突状态保持、brief 来源完整、证据目标缺失、过期证据、范围不匹配、hop 缺失、无交付回执、审计探针失效。
- 每个 completion pass 都能反向定位到发布者合同、每条验收标准和实际证据目标。
- 删除或篡改任一必需证据后，验收项可以解析为 `fail` 或 `unknown`，但 completion gate 必须不通过。
- 两个独立 Agent 的报告相互一致但缺少真实 E2E 证据时，仍不得完成。
- 至少用一个 Agentic-Dev 式真实长任务验证：交接、恢复、独立复验和最终交付均经过 Strict 控制。
- 职责分离测试确认：需要独立验证时，executor 或证据提交者不能签署自己的验收项。
- 两个并发 writer 产生连续且不重复的 seq；相同幂等 key 的相同事件只写一次，不同 payload 被拒绝。
- 合法事件领先 snapshot 时自动重建；半写尾记录、序号缺口和 snapshot 超前时 gate 停止。
- legacy v1 fixture 迁移前完整备份，迁移后缺证据的旧事实降级，且能切回只读备份。
- file、git commit、test report resolver 分别覆盖正常、越界路径、符号链接逃逸、摘要不匹配、旧 commit、过期报告和 scope mismatch。
- 默认 URL 语法 resolver 只能产生 unknown；可选网络 resolver 覆盖 allowlist、私网阻断、重定向、超时和响应大小上限。
- required 内容超过 8000 字符时返回 `BRIEF_REQUIRED_OVERFLOW`，不会生成截断 prompt。
- completion 每次重新解析必需证据；删除已通过证据后下一次 gate 必须不通过。
- handoff 只有 `enqueued` 或 `consumed` 而无匹配 `acknowledged` 时 completion 不通过；payload digest 或接收者不匹配时明确失败。
- worker 报告失败且只剩 best-effort runtime 日志时结果为 `failed` 或 `unknown`，不得从旧快照推断成功。
- AgentScope task completed、工具返回成功或 trace span OK 但缺少合同要求的真实证据时，验收项不通过；裁剪运行时 replay 日志不影响 Strict 控制账本重建。
- 宿主实时状态与旧 snapshot 冲突时，以实时观测更新对应 control event；宿主不可查询时状态为 `unknown`。

### 整体

- 使用者可以根据文档在 30 秒内人工选择 Lite 或 Strict。
- Lite 与 Strict 没有共享运行时依赖；删除任一 skill 不影响另一个运行。
- `context-transfer/v1` 有独立 schema 测试和双向兼容测试。
- 每个保留的机制在文档和测试中都映射到至少一个具体失败模式。
